# 知識庫同步（kb-sync）

把一批新的原始資料與現有知識庫比對後整合。整個流程分四個階段，**階段三（詢問）完成前，絕對不動 docs/ 任何檔案**。

## 本知識庫的結構與慣例（先牢記）

- Docusaurus 站台，內容在 `docs/`，分類：`platform/`（平台介紹）、`billing/`（帳務與金流）、`shipping/`（運費架構）、`contract/`（合約與財務）、`operations/`（營運 SOP）、`issues/`（已知問題）。
- 每份文件有 frontmatter：`sidebar_position` + `title`。每個分類有 `index.md`（或 `_category_.json`），新增文件後必須同步更新該分類的 `index.md` 連結清單與根目錄 `docs/index.md` 的目錄表。
- 圖片放 `static/img/haomaiplus/`，檔名用**語意化英文命名**（如 `project-payment-1.jpg`），不可沿用 Notion 匯出的亂數檔名。文內以 `/img/haomaiplus/xxx.jpg` 引用。
- 風格慣例：重要警告用 `:::danger` / `:::warning`、補充說明用 `:::info` / `:::note`、輕提醒用 `> 💡 **提醒**：`；結構化資訊優先用表格；流程用編號步驟或 code block 箭頭鏈。
- 名詞正規化：物流商統一寫「**日翊**」（原始筆記常誤植為日意/日益）；「好賣+」「好賣版」「超賣版」等名稱依現有文件用法。
- **敏感資訊紅線：帳號、密碼、內部功能密碼一律不得寫入知識庫文件**（站台會公開 build）。遇到時改寫為「請向團隊管理者索取」，並在報告中明確告知使用者已略過。其他疑似敏感內容（個人聯絡方式、金鑰、內部 IP）也先詢問再處理。
- **原始參考資料裡的明碼帳密也要遮蔽**：若新資料夾的原始檔案裡直接寫著實際密碼／金鑰（如「密碼：hU6$p@$J」），即使不打算寫進知識庫，也要在原始檔案裡把密碼本身遮蔽掉（如改成 `----`），避免明碼留在版本控制紀錄裡。**這是「原始資料夾永遠保持原樣」唯一的例外**：只准動密碼／金鑰等機密值本身，不改其他任何文字、不刪內容、不搬動或改名檔案。做法與時機見階段一步驟 6。

## 階段一：讀取與前處理

1. 列出新資料夾全部檔案（`find`），分清 Markdown 主文件與圖片附件。
2. 檢查主文件大小。若異常肥大，先用 `awk '{ if (length > 5000) print NR": "length }'` 找出超長行——Notion 匯出常內嵌 base64 圖片。用 `sed` 把 `data:image/...;base64,...` 替換為佔位字串，另存到 scratchpad 再讀，**不要修改原始檔**。
3. **完整讀取**清理後的新文件（分頁讀到最後一行，不可只讀開頭就下結論）。
4. 把現有 docs 全部串接成一份（`for f in $(find docs -name "*.md" | sort); do echo "===== FILE: $f ====="; cat "$f"; done > scratchpad/existing-docs.md`）並完整讀取。
5. 比對新資料夾的圖片與 `static/img/haomaiplus/` 現有圖片，判斷哪些是知識庫還沒有的。
6. **掃描新資料夾是否帶有明碼帳密／金鑰**：`grep -rn "密碼\|password\|帳號.*[:：]" 原始參考資料/YYYYMMDD/`。找到實際密碼值時（不是「請洽XX索取」這種提示文字，而是真的寫著一串密碼），直接在**原始檔案**中把密碼值改成 `----`（帳號本身若非機密可保留，只遮蔽密碼／金鑰）。這一步允許修改原始資料夾，且應在動手前後都留意：只換密碼字串，其他文字、格式、檔名一律不動。完成後在報告的「敏感內容」段落列出遮蔽了哪個檔案的哪一項。

   > 💡 若同一組帳密先前已被寫入過更早的 commit 歷史（`git log -p` 查得到明碼），這次遮蔽只能防止「之後」的版本再外流，無法清除舊 commit——這件事要在報告中明確告知使用者，是否要做 history rewrite 由使用者決定，不要自己動手。

## 階段二：逐節比對（不遺漏的關鍵）

建立**來源涵蓋清單**：把新文件依標題／分隔線切成小節，每一節（含零散的隨手記、會議記錄、日期註記如「6/15 新增」）都必須標上行號範圍並歸入以下五類之一，**任何一行都不能沒有歸屬**：

| 分類 | 定義 | 後續動作 |
| --- | --- | --- |
| ✅ 已收錄 | 內容與現有文件一致 | 不動作（但核對用語、數字是否完全一致） |
| 🆕 全新主題 | 知識庫完全沒有 | 規劃新文件位置 |
| ➕ 舊主題新細節 | 主題已有文件，但新資料多了細節 | 規劃如何融入既有文件 |
| ⚠️ 衝突 | 與現有文件數字、規則、說法矛盾 | **必須詢問使用者** |
| 🔒 敏感 | 帳密、金鑰、個資 | **必須詢問使用者**（帳密直接預設不收錄） |

比對時特別注意：

- **數字要逐一核對**（金額、費率、天數、代碼）。衝突常藏在數字裡——例如同一筆維護費一邊記 2,233、一邊記 22,333。發現時要自己驗算兩種算法各自的依據（如「合約總額 × 10% ÷ 12」vs「合約總額 ÷ 12」），在報告中把兩邊的推導都攤開，讓使用者能直接裁決。
- 零散筆記（「隨手記待整理」「會議記錄」）常混雜已收錄與未收錄內容，要逐條拆開判斷，不可整段跳過。
- 圖片也要納入清單：哪些已對應現有圖、哪些是新圖、新圖屬於哪一節。

## 階段三：報告差異並詢問（在此停下）

輸出一份結構化差異報告給使用者，格式：

1. **全新主題**（逐項列出，附行號與建議放置位置）
2. **衝突（需人工確認）**——每項寫清楚：現有文件記什麼、新資料記什麼、兩者的推導依據、你的建議
3. **舊主題的小幅補充**（可選擇性更新的項目）
4. **敏感內容與圖片差異**

然後**停止並等待使用者裁決**衝突與敏感項。若在互動情境可用 AskUserQuestion；否則在訊息結尾明確列出待決事項。使用者未回覆前不得進入階段四。

## 階段四：整合寫入

拿到裁決後才動筆。寫入前先做**架構重審**：

1. 重新檢視整個 docs/ 目錄結構，思考每個新主題放哪個分類、`sidebar_position` 排第幾最合理。相近主題放同分類、依使用頻率與邏輯順序排位，不是一律往後append。
2. **全新主題** → 建新文件。遵循現有文件的寫作風格（標題層級、admonition、表格、💡提醒），並加上與相關文件的交叉連結（如新 SOP 連回它對應的機制說明頁）。
3. **舊主題新細節** → 讀完整份目標文件後，把新內容**改寫融入最合適的段落**，讓通篇讀起來像一次寫成：
   - 數字更新：直接改在原處，必要時保留新舊對照（如「200,000（115 年 5 月前）／300,000（115 年 6 月起）」）。
   - 新規則：放進邏輯上所屬的章節，不是文末貼上。
   - 使用者裁決過的衝突：採用裁決值，並加 `:::warning 勘誤` 註記說明原始資料的錯誤值與正確依據，避免未來的人再被原始筆記誤導。
4. 搬運新圖片到 `static/img/haomaiplus/`，語意化重新命名，更新文內引用。
5. 更新索引：分類 `index.md` 的連結清單、根目錄 `docs/index.md` 的目錄表說明文字。
6. 名詞正規化與風格統一（日翊、全形標點、數字千分位）。

## 階段五：驗證

1. `npm run build` 必須成功（Docusaurus 會抓 broken links）。
2. `grep -rn "密碼\|password" docs/` 確認沒有帳密外洩（僅允許「不記載於本知識庫」類的提示文字）。
3. `grep -rn "密碼\|password" 原始參考資料/YYYYMMDD/` 確認這次新資料夾裡若曾有明碼密碼，已在階段一步驟 6 遮蔽為 `----`（不是要求資料夾內完全沒有「密碼」字樣，是確認密碼值本身不是明碼）。
4. 對照階段二的涵蓋清單逐項勾稽：每個 🆕 與 ➕ 項目都已落地、每個 ⚠️ 都依裁決處理、每張新圖都已引用。
5. 最終回報：新增了哪些文件、修改了哪些文件、衝突如何處理、略過了什麼及原因；若曾遮蔽原始資料夾裡的明碼帳密，列出遮蔽了哪個檔案的哪一項。若整合後發現衍生風險（如「未來對帳時新舊數字會對不上」），一併提醒。

## 品質底線

- 來源的每一行都要有歸屬——寧可多列一條「已收錄」也不可漏。
- 沒問過使用者之前，衝突項不准自行選邊寫入。
- 整合不是搬運：融入後的文件要能從頭讀到尾不突兀，沒有「補丁感」。
- 原始資料夾（原始參考資料/）永遠保持原樣，不修改、不刪除——**唯一例外是遮蔽裡面的明碼帳密／金鑰**（見上「本知識庫的結構與慣例」與階段一步驟 6），且僅限遮蔽密碼值本身，不做其他改動。
